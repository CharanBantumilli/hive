# Hive v1.0.13: Letters Between Queens

> Queens can write to each other, each in a conversation that lasts, with chains of letters kept in
> bounds and every hop logged. And a queen can be Claude Code itself, with all its tools: she writes
> and is written to like any other, paid for with an API key, and shown on the org chart.

## New

- **Queens write to each other.** Turn on `queen_mail` and a queen gets two tools: `list_queens`
  names the queens she can write to, and `message_queen` sends one a letter. The letter arrives in a
  session the other queen keeps for that writer (the same one every time, named after the writer
  in her session list) as `[Ava(queen_ava)]: ...`, the way a chat app's message does, so her memory
  and soul credit the writer. What she says there goes back the same way and wakes the writer: to the
  session of the letter her turn answers, or else the session the writer last wrote from. Her
  questions, the files she attaches and a reply that fails go back too, and the way back survives a
  restart. Off by default; `queens` limits who takes part. See
  [configuration.md](../configuration.md#queens-writing-to-each-other).
- **Chains in bounds, every hop logged.** A letter or reply is one hop deeper than the deepest letter
  or reply that entered its conversation since anyone else last spoke there; a message from someone
  else, a timer that fires or a worker's report starts a new chain. The hop past `max_depth` (8) isn't
  made, so two queens answering each other stop on their own, and a queen sends at most `daily_limit`
  (100) letters a day. Every hop is a line of `queens/mail.jsonl` (who, to whom, which sessions, what
  set it off and how deep, never the text), enough to draw how one push spreads from queen to queen.
- **A queen run by Claude Code.** Under `queen_mail.claude_code`, a queen is
  [Claude Code](https://docs.claude.com/en/docs/claude-code/overview) itself (`claude -p`), with all
  its tools. A letter to her runs a turn in a conversation she keeps for that writer, resumed every
  time, so she remembers each correspondent; letters that arrive while she works go in together as
  her next turn, and what she ends it with goes back to the writer. She writes to the other queens
  herself through a `hive` MCP server each of her runs gets, with a token good for that one
  conversation. The org chart shows her as a dashed card; opening it shows, read only, what was said
  and done in each of her conversations. `permission_mode`, `allowed_tools`, `cwd`, `model` and
  `timeout_minutes` set what she may do, where and for how long. See
  [configuration.md](../configuration.md#a-queen-run-by-claude-code).

  She pays with an Anthropic API key (`api_key`, and `api_base` for a gateway). Her runs inherit only
  what a program needs from Hive's environment, never Hive's credential key, provider keys or tokens.
  At most `max_parallel_turns` (2) of her turns run at once, each in its own process tree, which is
  stopped when a turn runs out of time or Hive stops.

## A Claude subscription is at your own risk

A Claude Code queen can also run on a Claude plan signed in in her own config folder, but only when
`"auth": "subscription"` says so. Running a plan unattended, on behalf of other agents, may go against
the terms of the plan, and Anthropic may limit or close the account. Hive does it only because you
chose it in so many words: it logs a warning when she first runs and marks her as such in the
dashboard. Whether it is allowed is between you and Anthropic, and what follows from it is yours
alone. The API key is the supported way.

Mind, too, what such a queen can reach: a queen who talks with strangers in a chat app can pass their
words on to her, so with `bypassPermissions` or Bash, a stranger is a few letters away from running
commands with the rights of the account Hive runs as.

## For code built on Hive

- New endpoints: `GET /api/claude-code-queens` and
  `GET /api/claude-code-queens/{queen_id}/conversations/{session_id}` (read only, for the dashboard);
  `GET /api/queen-mail/queens` and `POST /api/queen-mail/letters` (for a Claude Code queen's runs,
  with the `X-Queen-Mail-Token` of one conversation; the desktop token isn't asked for there).
- `framework.config.get_queen_mail_config()`, `QueenMailConfig` and `ClaudeCodeQueenConfig`;
  `framework.server.queen_mail.QueenMail` lives on `SessionManager.queen_mail`.
- `deliver_to_queen()` and `ChannelHost.send()` take a `correlation_id`, which marks the message's
  `client_input_received` and, once it enters the conversation, `client_input_committed`.

`aden-tools` is released at the same version. It hasn't changed, but the two packages pin each
other exactly.
